# LongPsych 中文心理对话检索技能

## 1. 技能用途

本技能通过 MCP 调用现有 LongPsychAgent 检索系统，从已建立索引的心理对话语料中检索并排序候选回复。

适用场景包括：

- 中文心理支持对话中的相似回复检索。
- 多轮心理会话中与当前诉求相关的历史对话证据检索。
- 长程心理会话中，为后续对话流程提供候选回复。
- 用户明确要求比较 Dense、ORCA 与 QR-Future 检索结果的场景。

本技能负责**检索与排序**，不独立生成心理咨询回复，不负责长期会话记忆，也不负责诊断或治疗决策。

## 2. 检索架构与默认流程

默认检索模式为 `qr_future`。在线检索流程如下：

1. 使用 `BGE-large-zh-v1.5` 将中文查询编码为 1024 维向量。
2. 使用 Dense FAISS 执行第一阶段候选召回。
3. 默认 QR-Future 候选池通常为 100 条；如未指定 `candidate_k`，由 FastAPI 服务采用其配置的默认值。
4. 五个冻结的 `QR_FUTURE_FULL` 折模型分别对候选进行评分。
5. 每一折使用与该折对应的 ORCA k=2 投影。
6. 对五折产生的原始排序分数求平均。
7. 根据平均排序分数确定最终候选顺序。
8. 返回调用方要求的 Top-K 候选及其原始标识和评分信息。

**必须遵守的检索协议：**

- QR-Future 的第一阶段候选召回使用 Dense，不得擅自替换为 ORCA 候选召回。
- `dense`、`orca` 和 `qr_future` 是三个不同的检索模式，不得将其混为同一流程。
- QR-Future 在线排序使用排序头。未来状态辅助头属于训练阶段的辅助目标，在线检索结果不提供未来心理状态概率。
- QR-Future 失败时，不得静默切换为 Dense 或 ORCA 并将其伪装成 QR-Future 结果。

## 3. MCP 工具选择

当前提供三个 MCP 工具。

### 3.1 常规检索：`longpsych_search_dialogue`

这是默认使用的主工具。除非用户明确要求其他检索模式，正常心理对话检索应优先选择 QR-Future。

默认参数：

- `mode`：`qr_future`
- `top_k`：`5`
- `candidate_k`：通常省略，使用服务端默认值；当前服务通常为 `100`

支持的模式：

- `dense`：使用现有 BGE Dense 检索。
- `orca`：使用现有 ORCA k=2 检索。
- `qr_future`：先进行 Dense 候选召回，再使用五折 QR-Future 排序。

### 3.2 检索模式对比：`longpsych_compare_retrievers`

仅当用户明确要求比较 Dense、ORCA 和 QR-Future 时使用。

调用时应：

1. 对三个模式使用完全相同的原始查询。
2. 调用一次对比工具。
3. 分别检查三种模式返回的候选和排序。
4. 解释候选集合与排序差异。
5. 不得把不同模式的分数当作经过统一校准、可以直接比较的概率。

该工具按顺序执行三种检索；`candidate_k` 仅作用于 QR-Future。

### 3.3 服务健康检查：`longpsych_retrieval_health`

在以下场景调用：

- 用户明确要求检查服务状态。
- 检索工具返回错误。
- 怀疑 MCP 或 FastAPI 服务不可用。
- 需要执行部署或集成验收。

正常检索成功时，不必每次额外调用健康检查工具。

## 4. 查询构造规范

### 4.1 单轮对话

优先使用用户当前的中文原始表达。不要把具体的心理困扰改写成过于宽泛、抽象或脱离语境的问题。

构造查询时应尽量保留：

- 当前主要困扰。
- 具体事件或现实处境。
- 用户明确表达的情绪。
- 用户当前希望讨论或解决的问题。
- 原始表达中的时间、人物关系和因果信息（仅保留检索所必需的内容）。

除非用户明确要求或检索任务确有需要，不要把中文查询翻译成英文。

### 4.2 多轮心理会话

当调用方能够提供相关历史背景时：

1. 将用户当前发言作为查询主体和主要锚点。
2. 只选择与当前心理议题直接相关的历史信息。
3. 仅在历史信息确实有助于检索时，才将其简洁附加到当前发言之后。
4. 不要把无关话题混入查询，例如与当前工作压力无关的旅游安排。
5. 不要用泛化的 LLM 改写完全替换用户当前发言。
6. 不要添加用户未表达的事实、诊断、动机或心理状态。
7. 不要加入不必要的姓名、联系方式、地址、账号标识等个人身份信息。

推荐的查询组织形式：

```text
用户当前发言：今天主管又给我加了任务，我感觉压力很大，不知道怎么安排。
相关历史背景：近期工作任务不断增加，担心无法按时完成；晚上经常因为工作安排而难以放松。
```

如果历史背景与当前诉求无关，应只发送当前发言，不要为了增加上下文而强行拼接历史内容。

**重要：** MCP 检索服务不会自行维护用户会话历史。历史上下文必须由调用该工具的 Agent 提供。

## 5. 输入参数约束

### `longpsych_search_dialogue`

- `query`：必填字符串，长度为 1–4000 个字符。
- `mode`：`dense`、`orca` 或 `qr_future`。
- `top_k`：整数，范围为 1–100，默认值为 5。
- `candidate_k`：可选整数，范围为 1–5000。
- `candidate_k` 仅适用于 `qr_future`。
- `candidate_k` 必须大于或等于 `top_k`。
- 通常省略 `candidate_k`，以使用服务端默认值。

### `longpsych_compare_retrievers`

- `query`：必填字符串。
- `top_k`：默认值为 5。
- `candidate_k`：默认值为 100，仅用于 QR-Future 候选池。

### `longpsych_retrieval_health`

- 不需要输入参数。

完整协议见 `references/tool-contract.md`。

## 6. 工具调用流程

### 常规检索流程

1. 明确当前需要检索的心理对话内容。
2. 根据本技能的查询构造规范形成查询字符串。
3. 除非用户明确指定其他模式，选择 `qr_future`。
4. 调用 `longpsych_search_dialogue`。
5. 检查工具返回的 `status`。
6. 读取候选回复及排序元数据。
7. 展示候选时保留原始 `response_text`，并明确说明它是检索结果。

### 对比检索流程

1. 对三个检索模式使用相同查询。
2. 调用 `longpsych_compare_retrievers`。
3. 检查 Dense、ORCA 和 QR-Future 三组结果。
4. 对比候选集合、最终排序和各自的模式内评分。
5. 说明不同模式的分数不可直接视为同一量纲的概率。

## 7. 结果解释与展示

重点字段：

- `response_uid`：候选回复的唯一标识。
- `response_text`：语料中保存的原始候选回复文本。
- `rank`：当前返回结果中的最终名次。
- `retrieval_score`：QR-Future 模式下的第一阶段 Dense 相似度分数。
- `qr_future_score`：五折 QR-Future 集成产生的原始排序分数。
- `candidate_rank`：候选在 QR-Future 重排前的 Dense 初始名次。
- `faiss_row`：内部 FAISS 行号。

解释结果时必须遵守：

- `qr_future_score` 是原始排序分数，不是概率、置信度、临床严重程度或回复质量百分比。
- 分数更负不代表检索失败。只能在相同模型与相同评分设置下谨慎比较分数。
- `candidate_rank` 与最终 `rank` 不同；QR-Future 可能提升或降低候选的最终名次。
- 高排名只表示模型在当前检索设置下将该候选排得更靠前，不代表该回复已经通过临床验证。
- 展示或引用候选时，保留 `response_text` 原文，不要擅自改写成仿佛来自语料的内容。
- 应明确区分“检索到的候选回复”和 Agent 自己生成的解释或回复。

## 8. 错误处理

如果 MCP 工具返回 `status="error"`：

1. 不得编造候选、标识或评分。
2. 在适当情况下调用一次 `longpsych_retrieval_health`。
3. 如果服务仍不可用，应明确告知用户当前检索服务暂时不可用。
4. 如果用户请求的是 QR-Future，不得静默降级到 Dense 或 ORCA。
5. 只有在用户明确同意更换模式后，才可以另行执行其他模式的检索，并清楚标注实际使用的模式。

注意区分 MCP 调用层的 `is_error` 与工具返回 JSON 中的业务字段 `status`。只要业务字段为 `status="error"`，就不能将该次调用解释为成功检索。

## 9. 能力边界与心理场景注意事项

本技能仅提供心理对话候选检索与排序，不负责：

- 独立生成完整的心理咨询或治疗回复。
- 对用户进行心理或精神疾病诊断。
- 根据原始排序分数估计用户的痛苦程度、未来心理状态或风险等级。
- 建立或维护用户长期记忆。
- 判断候选回复在具体个案中必然适用、安全或有效。
- 替代专业人员、专业评估或危机干预流程。

应将检索候选作为后续对话流程的参考证据。是否采用某条候选回复，应由具备相应约束和审核机制的后续 Agent 或应用逻辑决定。

## 检索结果解释边界（v1.2.1）

1. 不得直接比较 Dense、ORCA、QR-Future 不同检索模式的原始分数大小。
2. retrieval_score 和 qr_future_score 均为排序相关分数，不代表概率、置信度或临床指标。
3. 不得仅凭分数大小断言某种检索模式具有更强的语义理解能力。
4. 比较不同检索模式时，应重点分析候选内容、排序差异及候选集合重叠情况。
5. 对检索结果进行解释时，必须区分直接相关、部分相关和弱相关候选。
6. 不得根据候选回复反向推断用户没有明确表达的个人经历。
7. 如果候选回复出现实习、求职、恋爱等未经用户确认的具体背景，应明确指出其可能存在情境偏差。
8. 不得为了使检索结果显得合理而强行解释弱相关候选。
9. 检索结果是候选回复，不代表系统已经完成心理诊断或确定用户真实心理状态。


## 多轮检索执行硬约束（LangGraph V3）

本节规定 LongPsychAgent LangGraph V3 运行时的多轮上下文行为。它不改变 MCP Tool Contract V1。

1. **历史来源**：只允许从此前用户原始消息中选择历史内容；助手回复、检索候选和模型推测都不是用户事实。
2. **话题判断**：每次检索前判断 `initial`、`same_topic`、`return_to_topic`、`unrelated` 或 `uncertain`。
3. **历史数量**：最多选择两条与当前问题直接相关的历史用户原文；不得为了增加上下文而选择弱相关信息。
4. **原文可追溯**：每条历史引用必须是此前用户消息中逐字连续出现的片段，并保留来源轮次。
5. **确定性去重**：服务端对历史文本进行规范化去重；相同或近似重复内容不得反复注入。当前问题不得作为自己的历史背景。
6. **无关话题隔离**：`unrelated` 必须设置 `should_search=false`、清空历史选择，并且不得调用心理检索工具。
7. **当前消息优先**：`final_query` 必须以当前用户原始消息完整开头，不得改写、删减或用历史摘要替代。
8. **历史追加**：只有通过来源校验和去重的历史内容才能追加到当前消息之后；没有合格历史时直接使用当前消息原文。
9. **长度保护**：若追加历史会使查询超过 MCP 的 4000 字符限制，应舍弃历史背景并保留完整当前消息，不得截断当前消息。
10. **实际调用一致性**：传给 `longpsych_search_dialogue` 的 `query` 必须与上下文构造器产生的 `final_query` 完全一致。
11. **会话持久化边界**：当前部署由 LangGraph V3 Agent 使用 SQLite 持久化会话状态；恢复同一会话时使用相同 `thread_id`。MCP 检索服务本身仍然是接收单条查询的检索服务，不独立维护聊天历史或用户长期记忆。

对于不运行 LangGraph V3 的其他 MCP 宿主，上述历史管理、持久化和查询构造必须由宿主自行实现；不能仅凭安装本 Skill 就声称已经具备多轮记忆能力。
